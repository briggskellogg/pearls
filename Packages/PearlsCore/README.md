# PearlsCore

A dependency-free Foundation package for the first Pearls macOS and iPhone apps. It stores notes, web links, images, files, favorites, tags, and supplied OCR text. Saving, opening, and finding a pearl are the core operations.

**Build status:** all 20 XCTest cases compiled and passed on the user's Mac with Xcode 27.2 on November 8, 2026. See the app's `Release/STATUS.md` for platform and delivery evidence.

## Requirements

- Swift tools 5.9 or newer.
- macOS 14 / iOS 17 or newer.
- No network dependency, package dependency, account service, automatic OCR, or cross-device sync.

Add this folder as the local Swift package dependency `PearlsCore`. Import `PearlsCore` from the main app target. The share extension should write the app's separate pending capture inbox instead of writing library metadata.

## Main app integration

The app selects its own Application Support or App Group directory. Core does not look up entitlements or choose a fallback root, so an unavailable App Group cannot silently send content to the wrong library.

```swift
import PearlsCore

let store = try PearlStore(rootDirectory: applicationSupportURL)
let note = try store.addNote(title: "A thought", text: "Room to notice things.")
let link = try store.addLink(
    url: URL(string: "https://example.com/design")!,
    title: "A design reference"
)
let favorites = try store.search("design", favoritesOnly: true)
```

Every public store method is synchronous and can throw. Own one `PearlStore` inside the app's actor or a serial background queue. Do not run attachment copies or whole-library archive encoding on the main thread. The store uses an instance lock; Apple builds also use `NSFileCoordinator` for access by cooperating instances. The non-Apple compilation path has the instance lock only. All transactions reread current metadata before mutation, and no UI cache is treated as the authoritative library.

`refresh()` and its alias `load()` return **all** records, including Trash, ordered newest first. `search(_:)` hides Trash unless `includeDeleted: true` is passed. To show only Trash, filter `try store.refresh()` by `isDeleted`.

`item(id:)` returns an optional record and `contains(id:)` includes trashed records. A trashed capture remains a known identity and will not be recreated by inbox retry.

### Save originals

```swift
let item = try store.addAttachment(
    from: selectedURL,
    kind: .image,
    title: "A window",
    sourceURL: nil,
    tags: ["Architecture"],
    ocrText: recognizedText,
    contentType: "public.jpeg",
    originalFilename: "Window.jpg"
)
let storedOriginal = try store.attachmentURL(for: item)
```

Only `.image` and `.file` accept originals. The original bytes are copied without transcoding, thumbnail generation, or content modification. `contentType` is an optional application-supplied type identifier; the core does not guess it from a filename. The original filename remains display metadata, while a safe filename is used on disk. The caller must keep security-scoped permission active until `addAttachment` returns.

An original has a **25 MiB maximum** (26,214,400 bytes). Regular files only. Files beyond this limit fail before an original or metadata record is added.

### Share inbox ingestion

All create methods accept optional `id: UUID` and `createdAt: Date`. Use the pending capture's stable values:

```swift
if try !store.contains(id: capture.id) {
    _ = try store.addAttachment(
        from: inboxOriginalURL,
        kind: .file,
        title: capture.title,
        originalFilename: capture.originalFilename,
        id: capture.id,
        createdAt: capture.createdAt
    )
}
// Remove the pending entry only after the check/save above succeeds.
```

The equivalent `addNote` and `addLink` methods accept the same ID/date arguments. A duplicate create throws `itemAlreadyExists`; it does not overwrite an existing item. If an interrupted copy left a matching orphan original, the same-ID retry can reuse the identical bytes. Different bytes at that original path cause an error. UI should retain a failed pending capture for retry.

### Edit, favorite, and Trash

```swift
var edited = note
edited.text = "A revised thought"
edited.tags = ["Ideas"]
let saved = try store.save(edited)
_ = try store.setFavorite(true, for: saved.id)
try store.softDelete(id: saved.id)
try store.restore(id: saved.id)
```

`save(_:)` saves metadata. Existing creation dates, content kind, and original attachment identity cannot be changed through this method. It accepts new notes and links; new file/image records must use `addAttachment`. It returns the stored record with its new `updatedAt` timestamp. Dates generated by store factories are rounded to milliseconds.

Metadata editing uses the values supplied by the caller for editable fields, so retrieve a current record before composing a delayed edit. The first version does not implement collaborative editing or field-level merge.

Trash records retain all metadata and original bytes. There is deliberately no automatic purge or permanent-delete API in this first version.

## Finding things

Use `store.search(_:favoritesOnly:kind:includeDeleted:)` for current persisted results, or the pure function below for an already loaded snapshot:

```swift
let matches = PearlSearch.results(
    in: loadedItems,
    query: "blue room",
    favoritesOnly: false,
    kind: .image,
    includeDeleted: false
)
```

Every whitespace-separated query term must appear somewhere in the combined title, body, OCR, original filename, source URL, or tags. Matching ignores case, accents, and character-width variants using a fixed locale. Terms can appear in different fields. The empty query returns all items allowed by the filters. Results use descending creation date and ascending UUID for deterministic ties. This is a local text search; semantic search and network page extraction are not present.

## Portable backup and manual transfer

```swift
let data = try store.exportArchive()
// Supply this Data to the app's FileDocument exporter with extension .pearlsarchive.

let result = try otherStore.importArchive(importedData)
print(result.importedCount, result.skippedCount, result.repairedCount)
```

A `.pearlsarchive` file is one UTF-8 JSON document with all metadata and original files encoded as base64. It includes favorites, OCR text, tags, Trash, stable UUIDs, original filenames, content types, and dates. It needs no ZIP implementation or external dependency. The archive is **not encrypted**; the user should store it somewhere appropriate for its contents.

The encoded archive has a **100 MiB maximum** (104,857,600 bytes). Base64 increases original sizes, so the sum of raw files must be smaller than that. Export checks a conservative estimate before loading originals and checks actual encoded size before returning. The estimate reserves a small amount of overhead per original, so a library very close to the limit can be rejected. Imported data is limited before JSON decoding. The app's document reader should check selected file size before loading a large file into memory.

Imports are additive and validate the whole document before committing:

- New identities are added with their original UUIDs and creation dates.
- An exact identical record and original are skipped. Reimporting the same archive is safe.
- If the record is identical but its original file is missing, the original is restored from the archive and counted in `repairedCount`. Pure repairs preserve metadata and backup bytes exactly. Present but different originals are never overwritten.
- A different record or different original with the same UUID causes an `archiveConflict`. The user keeps both files and chooses how to reconcile; nothing is silently replaced.
- Missing, unreferenced, duplicate, incorrectly sized, oversized, or unsafe originals cause an error.
- Original files are written before the single metadata commit. A handled failure removes only files created by that attempt. A process interruption can leave harmless orphan files, which are preserved for future recovery.

The archive is the explicit manual way to transfer a library between Mac and iPhone. Changes are not automatically synced or merged between devices. Because an edited version of an existing UUID conflicts, a later archive is not an automatic incremental synchronization mechanism.

## Storage and recovery

```text
<provided root>/
  library.json
  library.previous.json
  attachments/<lowercase UUID>/<safe original filename>
  Recovery/library-damaged-<UUID>.json
```

The metadata format is versioned (`com.pearls.library`, schema 1), as is the archive (`com.pearls.archive`, schema 1). Each metadata write first validates and atomically records the prior snapshot as `library.previous.json`, then atomically replaces `library.json`. The metadata file is capped at 32 MiB. Atomic replacement protects readers from partial JSON writes; it is not a guarantee against hardware failure.

If the current metadata is malformed, the store validates the previous copy, preserves the damaged current file in `Recovery/`, and restores the previous snapshot. `recoveryNotice` reports the recovery and warns that the most recent edit may be absent. The app should present this notice visibly and retain a way to export surviving content. The format header is checked before version-specific items are decoded: a future schema is rejected even if its item fields are incompatible with this release. A newer primary is never replaced by an older backup, and an unsupported backup is preserved alongside the damaged primary.

If neither metadata copy is usable, the store throws `metadataUnrecoverable` and leaves both copies intact. If both metadata files are missing but original files remain, it throws `missingMetadataWithOriginals` instead of creating an empty library. Original bytes are never purged as part of recovery. The previous metadata copy is one rollback point; it is not a substitute for an exported backup.

A missing original does not hide its metadata record. Opening the original or exporting a complete archive raises an explicit error, allowing the app to report the affected item. Reads reject traversal paths, unexpected UUID directories, and symbolic links beneath the canonical library root. The supplied root is canonicalized during initialization, which handles the normal system paths used on Apple platforms.

## Models and errors

`Pearl`, `PearlAttachment`, and `PearlKind` are public Codable/Sendable values. The models and `PearlSearch` have no UI dependencies. `PearlStore` is a reference type with synchronized access and an explicit unchecked Sendable conformance. `PearlStoreError` is `LocalizedError` so UI can present a useful failure message. File-system errors are propagated when doing so preserves their underlying cause.

## Verification on a Mac

From this package directory:

```bash
swift test
```

The 20 XCTest cases cover persistent reload, source URL/filename/OCR search, diacritic folding and stable ordering, capture UUID retries, original byte and filename preservation, traversal and symbolic-link rejection, archive restoration and conflicts, missing-original repair without metadata changes, preservation of changed originals, Trash restore, malformed metadata recovery, preservation when both copies are invalid, incompatible future schemas in primary and backup files, missing-original export failure, separate store reload, and the per-original size limit.

These tests must pass on the intended Swift/Xcode toolchain before a release build. The app's separate tests should cover FileDocument integration, security-scoped picker access, share-extension ingestion, actual sandbox/App Group entitlements, and macOS/iOS presentation.
